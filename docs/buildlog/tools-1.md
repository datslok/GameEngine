## Tools outside the phases (part 1 of 2)

- `loading-screen` (Nov 11 2026): pipelines compiled on every core, with a loading screen. The user: "the game takes a very long time to respond after a fresh build", then "can we have a screen that says building shaders and a loading bar or something like that, rather than it just not responding for a min".
  - **Why:** after a build that changes the shaders the driver compiles every pipeline again, and the renderer made them one after another on the main thread before the first frame, the window not answering meanwhile.
  - **Measured first,** on the laptop: pointing NVIDIA's driver cache at an empty folder (`__GL_SHADER_DISK_CACHE_PATH`; `__GL_SHADER_DISK_CACHE=0` did nothing for Vulkan) stands in for a fresh build: the light lab took 199.5 s to start, about 5 s with a full cache.
  - **Asked first; the user chose both** of the two put to them (over a cache file of our own, which helps only starts whose shaders did not change, as the driver's cache already does): the builds on worker threads (`PipelineCompiler`, owned by the device) and a loading screen while they run.
  - **How:** the pipeline classes make their layouts at once and hand the slow part to the compiler; the first `get()` waits for its own build, so nothing else in the renderer changed. The screen is drawn by clearing rectangles, the text in a 5 x 7 block font, since no pipeline may be ready to draw it. The game's `onInit` runs while the pipelines compile. A build whose owner went before it started is skipped, so closing the window while loading quits at once.
  - **Measured after,** the laptop, the light lab: an empty cache 38.8 s (was 199.5), a full one 4.2 s (was about 5). Debug with validation and an empty cache 40.1 s, no validation errors.
  - **Found on the way:** the validation layer's one warning, an output of `triangle.vert` at location 5 that the cut-out depth prepass's `cut_out.frag` does not read ("not invalid, but the write to the unused output is discarded"). The prepass has paired the two since cut-outs came; probably the laptop's newer validation layer, since the desktop's reported nothing. Left for its own small fix.
  - **Checked:** the tests (release, tests first: the compiler's builds running together, its progress, errors coming back once, pipelines nobody takes destroyed or never built, its end waiting; the block font's glyphs, widths and spacing, the screen's layout, centring, bar and small windows); the release tests pass, the debug and release games build without warnings. **Not seen:** the loading screen itself by me (a hidden copy shows nothing while loading); the user is to look at it on the next fresh build.

- `cpp23` (Nov 11 2026): the engine builds as C++23 (`-std=c++23`), not C++20. The user asked why C++20; it had been the makefile's flag since its first commit, never a recorded choice.
  - **Why:** C++23 is nearly complete in GCC 16 and costs one flag. It brings `std::mdspan` (the grids: the distance field, froxels, atlases), `std::flat_map` (a map in a fixed order, for determinism), deducing `this` (one member function for `const` and not), `std::print` and smaller fixes. C++26 (static reflection, which could generate the settings' `visit()` lists and the state hash) waits until its support is stable.
  - **How:** only the flag changed. No code uses C++23 yet: its features are to be taken up where they clearly help, not by rewriting working code.
  - **Checked:** the debug game and the release tests build without a warning or an error; the release tests pass.

- `command-line-control` (Oct 29 2026): commands to a running game from the command line. The user: "make sure the game engine is usable as a tool for AI ... control all the features from a command line, and still see the effects in the GUI".
  - **Explained first; the user chose** a local socket (127.0.0.1) with `game.exe --send` as its client, over the game's own console (an AI's shell calls are separate processes, so it cannot keep a console open between them) and a command file the game watches (clumsy replies, races, a disk poll every frame). It works across separate calls, and replies (values, errors) come back.
  - **The scope, narrowed by the user:** an AI should develop the game, not play it, so game actions and raw key injection were dropped. What matters is the settings, the camera, the simulation's clock and seeing the picture. The future editor's operations will be commands in the same registry, its buttons issuing them, so an AI can do whatever its windows can and undo comes from the same list (ROADMAP, phase 14's level editor).
  - **Settings came almost free:** every tunable value already has one `visit()` description (the F5 UI and `settings.cfg` walk it), so `set`, `get`, `list` and `reset` cover every setting now and later with no list of their own. `setSetting` was added to say exactly what happened to one field (set, clamped, refused, unknown, start-up only), which the file's loader, forgiving by design, had folded into warnings.
  - **Commands run between frames,** before the frame's time is measured, so a long screenshot or step is not game time and causes no burst of catch-up ticks; `step` runs the loop's own `runTick`, and a test checks that stepping the demo reaches the very state of ticking it.
  - **The screenshot** reuses the golden images' off-screen capture at the window's size, so the picture is the game's without the debug UI, and anti-aliasing is settled for it (the live view blurs for a frame or two after).
  - **Checked:** the tests (release, tests first: splitting and quoting, replies, near names, help, settings set, clamped, refused, unknown and start-up only, get, list and reset by key and group, pause and step, the camera placed and held, a game that cannot place it, the socket's round trip with a 200 KB reply, two clients, a taken port, no game listening, the launch options); the release tests pass, the debug game builds without warnings.
